# Дизайн: мгновенное внесение счёта с типом игры и счётом по шарам, полный FAQ

Дата: 2026-09-17

## Контекст

Бот только что переведён на работу исключительно в общем групповом чате
(см. commit "Group-only bot" — GroupOnlyMiddleware, GROUP_CHAT_ID обязателен).
Следующий шаг — убрать вторую половину старого «личного» флоу: подтверждение
счёта оппонентом кнопками ✅/❌. Группа маленькая, доверенная, все видят
заявку сразу в чате — подтверждение больше не нужно, важнее удобство и
детализация счёта (тип игры, счёт по шарам).

## 1. `/score` — новый формат, без подтверждения

```
/score @user1 @user2 <тип> <X:Y> <счёт1> [<счёт2> ...]
```

Пример: `/score @alex @petya moscow 2:0 8:7 8:6`

- `@user1 @user2` — два игрока матча. Заявитель (тот, кто пишет команду)
  может не быть ни одним из них — любой участник группы может внести
  результат чужого матча.
- `<тип>` — `moscow`/`москва` или `america`/`америка`, без учёта регистра.
- `<X:Y>` — агрегат: сколько партий выиграл `user1`, сколько `user2`.
  Используется только для проверки ввода, отдельно не хранится. Может
  быть равным (это не партия, а сводка), например `1:1`.
- `<счётN>` — счёт по шарам одной партии, например `8:7`. Каждая такая
  партия — как и раньше, атомарная единица рейтинга Glicko-2 (важно
  только, кто выиграл партию; величина изменения рейтинга от маржи
  счёта не зависит). Ничья в счёте партии невозможна.

Валидация (заявка отклоняется с понятным сообщением, если нарушено):
- количество перечисленных счетов по шарам ≠ X + Y;
- количество партий, где выиграл `user1` (первое число больше второго),
  ≠ X (аналогично для `user2` и Y);
- один из счетов по шарам — ничья (первое число равно второму);
- `user1 == user2`;
- один из `user1`/`user2` не найден или неактивен (не в whitelist).

Заявка применяется **сразу**, без подтверждения: создаются `Match`-записи
сразу со статусом `CONFIRMED`, рейтинги обоих игроков пересчитываются
немедленно (переиспользуем существующий `confirm_session`/
`rebuild_all_ratings`), и в этом же сообщении в группе бот показывает
итоговое изменение рейтинга обоих игроков — то, что раньше показывалось
только после нажатия ✅.

`reported_by` = telegram_id заявителя (не обязательно один из игроков) —
нужен, чтобы `/cancel` мог проверить, кто вправе отменить заявку.

## 2. Модель данных

- `Match`: добавить `game_type: str | None` (`"moscow"` / `"america"`).
- `Match`: убрать `reminder_sent`, `escalated` — эти поля были нужны
  только для крон-джоба напоминаний/эскалации, который убираем (см. п.4).
- `MatchStatus`: оставить только `CONFIRMED` и `CANCELLED`. `PENDING` и
  `DISPUTED` больше никогда не возникают — убираем оба значения и весь
  код, который на них ветвился.

⚠️ **Совместимость с БД на сервере**: `init_db()` использует
`Base.metadata.create_all`, который не умеет ни добавлять колонки в уже
существующую таблицу, ни удалять старые. Если на сервере уже есть
`data/billiard.db` со старой схемой — перед деплоем этой версии нужно
либо удалить файл (если реальных матчей ещё не заводили), либо вручную
выполнить `ALTER TABLE matches ADD COLUMN game_type VARCHAR(16)` (колонки
`reminder_sent`/`escalated` можно просто оставить висеть неиспользуемыми
в SQLite — они не мешают). Это шаг ручного деплоя, не код.

- `handlers/confirm.py` — удаляется целиком (кнопки ✅/❌, `on_confirm`,
  `on_dispute`).
- `handlers/admin.py` — убрать `cmd_resolve` (`/resolve` работал только
  со статусом `DISPUTED`, который больше не возникает). `/editmatch`
  остаётся — он не зависит от статуса и остаётся единственным способом

- `bot/main.py` — убрать `_check_pending_reminders` целиком и её
  регистрацию в `AsyncIOScheduler` (напоминания об неподтверждённых

  неподтверждёнными).
- `services/match_service.py` — убрать `get_pending_matches_older_than`
  (использовался только в убираемом крон-джобе).
- `bot/config.py` — убрать `reminder_hours`, `escalation_hours` из
  `Settings`.
- `.env.example`, `README.md` — убрать `REMINDER_HOURS`/`ESCALATION_HOURS`
  и описание старого флоу подтверждения, обновить под новый флоу.

## 4. `/cancel` — единственная страховка от ошибок

`/cancel [session_id]` — заявитель отменяет **свою** заявку (проверка по
`reported_by`, как и сейчас). Раз матчи сразу `CONFIRMED`, отмена теперь
означает: перевести матчи сессии в `CANCELLED` и пересчитать рейтинги
(`rebuild_all_ratings`), а не просто снять статус `PENDING`.

- Без аргумента — ищем последнюю подтверждённую (не отменённую) сессию,
  заявленную этим пользователем (аналог текущего
  `find_latest_pending_session_by_reporter`, но по `CONFIRMED`).
- `cancel_session` меняется: проверка `status == CONFIRMED` вместо
  `PENDING`, плюс вызов `rebuild_all_ratings` после отмены.

Ограничений по времени на `/cancel` не вводим (как и сейчас).

## 5. Вывод счёта

- Ответ на `/score`: тип игры, список партий со счётом по шарам, и
  изменение рейтинга обоих игроков (объединяем то, что раньше было в
  сообщении `/score` + в сообщении после подтверждения).
- `/history @user`: показывать тип игры и счёт по шарам на партию вместо
  голого счёта, например `Москва, 8:7`.
- `/stats`: без изменений — только W/L и общий рейтинг, без детализации.

## 6. `/faq` — полный список команд участника

Переписать `FAQ_TEXT`/добавить команды: `/start`, `/score` (новый формат
с примером и объяснением валидации), `/cancel`, `/top`, `/stats`,
`/stats @user`, `/history @user`, `/faq`. Админские команды (`/adduser`,
`/removeuser`, `/editmatch`) не включаются — FAQ адресован участникам, не
админам.

## Не в этой задаче

- Старый формат `/score @opponent X:Y [X:Y ...]` не поддерживается —
  полностью заменяется новым.
- Оффлайн-миграция существующей SQLite БД — ручной шаг деплоя, не код
  (см. п.2).
